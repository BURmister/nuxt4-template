# Архитектура и правила

## 1. `shared` и `widgets`

Правило простое:

- `shared` — универсальный элемент, который не знает о конкретной странице
- `widgets` — готовый экранный блок, который собирает shared-компоненты и локальную логику

Примеры:

- `shared/button/Primary`
- `shared/card/article/Normal`
- `widgets/home/Hero`
- `widgets/articles/List`

## 2. Паттерн страниц

Типовая страница собирается так:

1. данные через `useApiFetch` или `useApiPaginatedList`
2. SEO через `$defaultMeta` + `useSeoMeta`
3. layout через `WidgetsPageLayoutComponent`
4. секции через `WidgetsPageSectionComponent`

Это ровно тот паттерн, который удобно масштабировать дальше на каталог, блог, help-страницы и marketing pages.

## 3. Stores в шаблоне

Оставлены только те stores, которые полезны почти в любом проекте:

- `burgerMenu.js`
- `bottomTabs.js`
- `useConfirm.js`
- `selection.js`

То есть храним инфраструктуру UI, а не доменную бизнес-логику.

## 4. Server API

Локальный `server/api` нужен не ради “моков ради моков”, а чтобы:

- сразу работал SSR
- были примеры реальных запросов
- команда могла верстать страницы без ожидания backend

Когда внешний API будет готов, переключение делается через `runtimeConfig.public.apiPrefix`.

## 5. Что намеренно не переносилось

Из исходного проекта не переносились:

- корзина
- избранное
- checkout
- профиль
- auth-flow
- доменные карты, captcha и продовые интеграции

Идея шаблона в том, чтобы ускорять старт, а не тянуть в новый проект чужую бизнес-логику.
